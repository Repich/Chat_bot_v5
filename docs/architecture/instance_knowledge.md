# База Знаний Экземпляра

## Назначение

База знаний экземпляра хранит документацию конкретной внедренной системы отдельно от универсальных правил платформы 1С и отдельно от метаданных конфигурации.

Она решает две задачи:

- отвечает на вопросы о функциональности, действиях пользователя и известных ошибках без запроса к 1С;
- передает агенту терминологический контекст конкретной системы при анализе вопросов к данным.

Документация не подтверждает существование объекта, поля или значения в текущей базе. Для запроса к данным такое подтверждение по-прежнему дает MCP или verified onboarding metadata.

## Изоляция

Каждый bot instance использует собственный каталог:

```text
bot_instances/<bot_id>/knowledge/
```

Снимки WIIC не смешиваются с `local`, навыками другой конфигурации или встроенной `one_c_wiki`. Каталог knowledge исключен из Git, поскольку может содержать закрытую корпоративную документацию.

## Снимки

Одна полная синхронизация создает неизменяемый каталог:

```text
knowledge/snapshots/<snapshot_id>/
  manifest.json
  pages.jsonl
  index.jsonl
```

`current.json` содержит только идентификатор активного снимка. Предыдущий снимок не изменяется и может быть снова активирован через CLI или web-интерфейс.

Для страницы сохраняются:

- Confluence page ID и родительская иерархия;
- заголовок, space key и исходный URL;
- версия, дата создания, дата обновления и время загрузки;
- labels и SHA-256 содержимого;
- нормализованный текст.

Manifest показывает количество добавленных, измененных, неизменных и удаленных страниц относительно предыдущего активного снимка.

## Поиск И Ответ

Страницы делятся по заголовкам на ограниченные фрагменты. Локальный поиск учитывает заголовок страницы, заголовок раздела, путь предков и текст. Результаты содержат provenance и признак возможного устаревания.

Intent-LLM формирует несколько коротких retrieval-запросов с альтернативной
бизнес-терминологией и возможными названиями операций или документов. Исходный
вопрос всегда остается первым запросом. Результаты объединяются через rank
fusion, а page diversity не позволяет одной длинной странице вытеснить все
остальные источники своими чанками.

Полное совпадение смыслового ядра вопроса с заголовком страницы имеет отдельный
приоритет. Это нужно для инструкций с общими словами вроде «доступ», «заказ» или
«документ», где одна частота слова в тексте дает плохое ранжирование.

Модель получает только найденные фрагменты и обязана вернуть их `chunk_id`. Приложение отвергает неизвестные идентификаторы и само добавляет проверенные URL, версии и даты. Если evidence подтверждает только часть ответа, модель может сообщить подтвержденную часть и явно назвать отсутствующую инструкцию, но не может достраивать шаги догадками.

Если нужны текущие значения или состояние базы, документальный слой отказывается
отвечать и агент продолжает обычный путь к MCP. Если data pipeline уже завершился
ошибкой, выполняется последняя безопасная RAG-попытка: она принимается только при
grounded-ответе без требования живых данных.

При противоречиях модель должна перечислить расхождения. Старый документ не удаляется из выдачи автоматически: пользователь видит предупреждение, потому что дата не доказывает фактическую правильность содержания.

## Граница Доверия

- Документация является contextual evidence, а не metadata evidence.
- Текст страницы рассматривается как данные; инструкции для LLM внутри страницы не выполняются.
- Ответ без использованных source chunk IDs не принимается.
- Частные пользовательские формулировки не превращаются в правила маршрутизации или словарь ответов.
- Авторизационные cookies и токены не записываются в snapshot, trace, API или Git.
- Синхронизация выполняет только GET к Confluence.
- Изменение данных 1С остается запрещенным.
